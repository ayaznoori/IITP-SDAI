## Block 1 — Why Does This Matter?

> 🎯 **Instructor Note:** This audience already learned, in the AI-assisted debugging and review session, that AI-generated tests risk confirming what code currently does rather than what it should do. This session is the hands-on, practical follow-through: actually using AI to generate tests, actually validating them, and building the review discipline that makes this genuinely safe rather than a false sense of coverage. Open by naming that this is the practical half of something already introduced conceptually. Wait after the opening question.

**[Script:]**

"You already know the theoretical risk: a test generated by looking at existing code can confirm that code does what it currently does, not that it does what it should do. Today is about actually using AI for testing in practice, with that risk in mind from the start, rather than as an afterthought.

Writing thorough tests by hand is slow, and it is easy to only think of the test cases that come naturally to mind — the happy path, maybe one obvious edge case — while missing others that only become apparent with more systematic thinking. AI is genuinely good at generating a broad set of test ideas quickly, including cases you might not have thought of yourself. That is real, practical value. But generating a test is not the same as having a good test, and having tests that pass is not the same as having tests that actually protect your code.

Today covers four connected practical skills: using AI to brainstorm test ideas and generate actual test code, actually running those generated tests and debugging the failures that come up — because generated tests do fail sometimes, for real reasons — engineering-led review of AI-generated tests, where a human makes the final call on whether a test is actually meaningful, and finally, using AI tools specifically to review pull requests, applying everything from the earlier code review and PR discipline sessions through an AI-assisted lens. By the end, you will have a genuinely practical, hands-on workflow for AI-assisted testing that produces real test coverage, not just a large number of passing assertions."

## Block 2 — Using AI to Generate Test Ideas and Test Cases

### 2A — Two Distinct Uses: Ideas Versus Code

**[Script:]**

"There are two genuinely different ways to use AI for testing, and it is worth treating them as separate steps rather than blending them together. First: generating test ideas — a list of scenarios and conditions worth testing, in plain language, before any test code exists. Second: generating the actual test code for a specific scenario, once you have decided it is genuinely worth testing.

Separating these matters because the first step is where AI's breadth is most valuable — surfacing scenarios you might not have thought of — and the second step is where careful review matters most, since that is where actual assertions get written that either do or do not meaningfully verify something."

> 🎯 **Instructor Note:** Write this two-step distinction on the board and keep it visible for the block.

```
Step 1 — Generate test IDEAS (plain language, before any code)
  "What scenarios should I be testing for this function?"

Step 2 — Generate test CODE (for specific, chosen scenarios)
  "Write a test for the empty-list case we identified."

Treating these as separate steps means you deliberately choose 
which ideas are actually worth turning into code, rather than 
accepting whatever a single generation pass happens to produce.
```

---

### 2B — Generating Test Ideas

**Predict before running: What will happen?**

> 🎯 **Instructor Note:** Show this function on the board. Ask: "Before seeing any AI-generated suggestions — brainstorm test ideas for this function yourselves, right now, as a group." Give the room genuine time to generate their own list first; this makes the comparison against the AI-generated list far more meaningful.

**Demo 1 — Generating test ideas for a function (whiteboard-friendly)**

```python
def apply_discount(price: float, discount_percent: float) -> float:
    return price * (1 - discount_percent / 100)
```

```
Prompt: "List test scenarios worth covering for this function. 
Don't write test code yet, just describe the scenarios."

Likely AI-generated list:
1. Normal case — a reasonable price and discount percent
2. Zero discount (0%) — price should be unchanged
3. 100% discount — price should become 0
4. Discount over 100% — result would be negative; is that valid?
5. Negative price — is this a valid input at all?
6. Negative discount percent — would this increase the price?
7. Zero price
8. Very large price — floating point precision considerations
```

**[Script:]**

"Compare this against whatever your own group generated. Items 1 through 3 are likely ones most people think of naturally — the happy path and the two obvious boundary values. Items 4 through 6 are exactly the kind of scenario that is easy to overlook when brainstorming manually, because they involve questioning whether an input is even valid in the first place, not just picking different numbers within an assumed-valid range.

This is the genuine, practical value of this first step: not writing better code than you could write yourself, but surfacing a more complete list of scenarios worth deciding about, faster than manually brainstorming alone typically produces."

> 🎯 **Instructor Note:** Ask: "Item 4, discount over 100%, is on this list — but is that automatically a bug that needs fixing, or could it be entirely acceptable depending on the actual business requirements?" Answer: it depends entirely on the requirements, which the AI has no access to — this is exactly why generating ideas is a starting point requiring human judgment, not a final answer. The list surfaces a *question worth asking*, not an automatic verdict that every item represents something broken.

### 2C — Generating Test Code for Chosen Scenarios

**[Script:]**

"Once you have decided which scenarios are actually worth testing — a decision requiring your own knowledge of the actual requirements — the next step is generating the real test code for those specific, chosen scenarios."

**Demo 2 — Generating test code for a decided scenario (whiteboard-friendly)**

```python
# Decision: negative discount_percent should raise a ValueError, 
# per the actual business requirement — this was NOT something 
# the AI could have known on its own; a human made this call.

def apply_discount(price: float, discount_percent: float) -> float:
    if discount_percent < 0:
        raise ValueError("Discount percent cannot be negative")
    return price * (1 - discount_percent / 100)

# Prompt: "Write a test confirming apply_discount raises ValueError 
# for a negative discount_percent."

def test_apply_discount_negative_percent_raises():
    with pytest.raises(ValueError):
        apply_discount(100, -10)
```

**[Script:]**

"Notice the actual behavior — raising `ValueError` for a negative discount — was a decision made by a human, based on the real business requirement, not something inferred purely from the AI's own reasoning about what 'should' happen. The AI generated the test code implementing that already-decided behavior; it did not make the actual design decision. This ordering matters: idea generation surfaces the question, a human answers the question based on real requirements, and only then does code generation produce a test verifying that specific, human-decided answer."

> 🎯 **Instructor Note:** Ask: "What would have gone wrong if you had asked the AI to both decide what should happen for a negative discount AND write the test for it, in a single step, without your own explicit decision in between?" Answer: the AI might generate a plausible-sounding but incorrect assumption — perhaps deciding a negative discount should just be silently treated as zero, when your actual business requirement is that it must raise an error — and then confidently write a test that locks in that wrong assumption, looking just as legitimate as a test verifying the correct behavior.

**Recap of Block 2 before moving on:**

- Separate generating test ideas in plain language from generating actual test code for specific, chosen scenarios
- Idea generation is valuable for surfacing scenarios that are easy to overlook, especially edge cases and input-validity questions, not just boundary values within an assumed-valid range
- A generated idea is a question worth asking, not an automatic verdict — human judgment, grounded in real requirements, decides what the correct behavior actually is
- Test code generation should happen only after that human decision is made, verifying an already-decided behavior rather than inventing one

## Block 3 — Validating Tests by Running and Debugging

### 3A — A Generated Test Is a Claim, Not a Fact

**[Script:]**

"A generated test, before it has actually been run, is a claim about behavior — it has not yet been confirmed to even be syntactically valid, let alone correct. Running it is the first real check, and debugging any resulting failure is where you discover whether the failure means the test is wrong, or the code is wrong, or both."

---

### 3B — Running Generated Tests and Diagnosing a Failure

**Predict before running: What will happen?**

> 🎯 **Instructor Note:** Show this generated test on the board, alongside the actual function. Ask: "Before running this — does it look correct to you? What do you predict happens when it actually runs?" Let the room examine it and guess before revealing the actual result.

**Demo 3 — Running a generated test that fails (whiteboard-friendly)**

```python
def apply_discount(price: float, discount_percent: float) -> float:
    if discount_percent < 0:
        raise ValueError("Discount percent cannot be negative")
    return price * (1 - discount_percent / 100)

# Generated test:
def test_apply_discount_hundred_percent():
    result = apply_discount(100, 100)
    assert result == 0

# Running this test: PASSES
```

```python
# A second generated test, from the same batch:
def test_apply_discount_floating_point():
    result = apply_discount(19.99, 15)
    assert result == 16.99

# Running this test: FAILS
# AssertionError: assert 16.9915 == 16.99
```

**[Script:]**

"The first test passes cleanly. The second fails — and this is exactly the moment where debugging discipline from earlier in the course applies directly. The actual computed result is 16.9915, not exactly 16.99. This is not a bug in `apply_discount` — it is a floating point precision issue: multiplying 19.99 by 0.85 does not produce a perfectly round number, and the generated test's assertion assumed it would. The test itself has a bug, not the function."

> 🎯 **Instructor Note:** This is a genuinely common, realistic category of generated-test bug worth dwelling on. Ask: "Given this failure, what are your two options, and how would you decide between them?" Answer: either the test's expected value is wrong and needs correcting — likely rounding to a reasonable number of decimal places, or using an approximate-equality comparison instead of exact equality — or, in principle, the failure could reveal an actual bug in the function itself. Here, it is clearly the former: the function's math is correct, and the test's assumption about exact floating point equality was the actual mistake.

---

### 3C — Fixing the Test, Not the Code, When the Test Is Wrong

**Demo 4 — Correcting a generated test's flawed assertion (whiteboard-friendly)**

```python
def test_apply_discount_floating_point():
    result = apply_discount(19.99, 15)
    assert result == pytest.approx(16.99, abs=0.01)

# Running this corrected test: PASSES
```

**[Script:]**

"`pytest.approx` allows a small, explicitly bounded tolerance instead of demanding exact floating point equality — the appropriate fix here, since the function's actual behavior was correct all along and the test's original assertion was simply too strict for how floating point arithmetic actually works. This is the core discipline of this entire block: running a generated test is not the finish line, it is the start of a real investigation, exactly the same debugging mindset from earlier in the course, now applied specifically to the AI-generated test's own correctness rather than only to application code."

> 🎯 **Instructor Note:** Ask a synthesis question: "If you had simply deleted this failing test instead of investigating and fixing it, what would you have actually lost?" Answer: real test coverage for a genuinely valid, useful scenario — deleting a failing generated test without understanding why it failed risks discarding a legitimate check purely because it was inconvenient, rather than because it was actually wrong to test. The investigation is what tells you whether to fix the test, fix the code, or in rare cases genuinely conclude the scenario is not worth testing after all.

**Recap of Block 3 before moving on:**

- A generated test is an unverified claim until it has actually been run; running it is the first real validation step
- A failing generated test requires genuine debugging to determine whether the test's own assertion is flawed, the underlying code has a real bug, or both
- Floating point precision issues are a common, realistic source of incorrect assertions in generated tests, fixed with an appropriate tolerance rather than exact equality
- A failing test should never simply be deleted without investigation — that risks discarding legitimate coverage rather than correcting a real mistake

## Block 4 — Engineering-Led Test Review

### 4A — Why a Human Makes the Final Call

**[Script:]**

"Everything in Blocks 2 and 3 already involved human judgment at key points — deciding which ideas to turn into code, deciding whether a failure meant the test or the code was wrong. Engineering-led test review formalizes this as a deliberate, final review pass over an entire generated test suite before it is considered genuinely done, checking specifically for the structural risks already known from the debugging and review session: tests that confirm current behavior rather than correct behavior, and tests that provide an illusion of coverage without actually verifying anything meaningful."

---

### 4B — Reviewing for Meaningful Coverage, Not Just Passing Tests

**Predict before running: What will happen?**

> 🎯 **Instructor Note:** Show this generated test on the board. Ask: "This test passes. Before I say anything else — does passing mean this is actually a good, meaningful test? Look closely." Give the room real time to scrutinize it.

**Demo 5 — A passing test that verifies almost nothing meaningful (whiteboard-friendly)**

```python
def test_apply_discount_returns_a_number():
    result = apply_discount(100, 10)
    assert result is not None
```

**[Script:]**

"This test passes. It is also nearly worthless as a check on correctness — it confirms the function returns something, not that it returns the *correct* something. A completely broken implementation of `apply_discount` that returned any number at all, including a wildly wrong one, would still pass this exact test. This is a real, common pattern in generated test suites: a test that is technically valid, technically passing, and contributes essentially nothing to actual confidence in the code's correctness."

> 🎯 **Instructor Note:** This is the central teaching point of the entire block. Emphasize directly: "A green checkmark next to this test tells you nothing useful. If your review process only checks 'do the tests pass,' a test suite full of assertions like this one looks exactly as healthy as a test suite that actually verifies real behavior — until the day a real bug slips through a test that was never actually checking for it."

---

### 4C — A Practical Review Checklist for Generated Test Suites

**[Script:]**

"A deliberate review pass over a generated test suite should check for several specific things, beyond simply confirming the suite runs and passes."

> 🎯 **Instructor Note:** Write this checklist on the board — this is the practical takeaway of the block.

```
Engineering-led review checklist for generated tests:
- Does each assertion check a SPECIFIC, correct expected value, 
  not just "returned something" or "didn't crash"?
- Are known edge cases from Block 2's idea list actually covered, 
  not just the happy path?
- Would this test actually FAIL if a real, specific bug were 
  introduced into the code? (Mentally introduce a bug and check.)
- Does the suite avoid redundant tests that check the same 
  behavior repeatedly in slightly different phrasing?
- Are test names and structure consistent with the codebase's 
  existing test conventions?
```

**[Script:]**

"The third item — mentally introducing a specific bug and asking whether the test suite would actually catch it — is the single most effective check here, and worth doing deliberately rather than skipping. Take the `apply_discount` function, imagine changing the calculation to `price * (1 + discount_percent / 100)` — an inverted sign, a completely plausible real typo — and ask which of your tests would actually catch that. The 'returns a number' test would not. A test with `assert result == 90` for a 10% discount on 100 absolutely would."

> 🎯 **Instructor Note:** Ask the room to actually do this exercise: "Take the full set of tests from Demos 2 through 5 in this session. If someone introduced that exact sign-inversion bug, which specific tests would catch it, and which would not?" Let them work through it concretely — this hands-on exercise is what makes the review checklist feel like a real, applicable skill rather than an abstract list.

**Recap of Block 4 before moving on:**

- Engineering-led review is a deliberate, final pass checking that a generated test suite provides real coverage, not just that it passes
- A passing test is not automatically a meaningful test — a test that only checks a result is "not None" would pass for a badly broken implementation just as easily as a correct one
- Mentally introducing a specific, plausible bug and checking which tests would actually catch it is the most effective review technique
- A meaningful review checklist covers specific assertions, real edge case coverage, actual bug-catching ability, redundancy, and consistency with existing conventions

### 5B — Prompting an AI Reviewer Specifically About Test Quality

**Predict before running: What will happen?**

> 🎯 **Instructor Note:** Ask: "Based on the risk-specific prompting discipline from the debugging and review session, what do you expect a generic 'review this PR' request to catch about test quality, compared to a request specifically asking about test meaningfulness?" Answer: a generic review is likely to comment on code style and obvious issues, but is unlikely to specifically flag something like the "returns a number" test from Block 4 as low-value, since that requires deliberately reasoning about what each test actually verifies — exactly the kind of check that needs to be explicitly requested to reliably happen.

**Demo 6 — Prompting specifically for test quality in a PR review (whiteboard-friendly)**

```
WEAK PROMPT:
"Review this PR."

STRONGER PROMPT:
"Review this PR's test suite specifically. For each test, assess: 
does it check a specific correct value, or just that something

plausible real bug were introduced into the function it tests? 
Flag any test that provides only superficial coverage."
```

**[Script:]**

"This is the exact same principle from the original PR-review session — a generic prompt surfaces generic, surface-level comments; a prompt naming the specific thing you actually want checked surfaces a genuinely useful, targeted review. Here, that specific thing is test meaningfulness itself — precisely the Block 4 checklist, now applied by an AI reviewer as a structured first pass, before a human engineer does the final review."

### 5C — Where This Fits in the Overall Workflow

**[Script:]**

"Put together, this is the complete practical loop for this entire session: generate test ideas, decide which matter based on real requirements, generate test code for those decisions, run and debug until the tests are actually correct, review the suite yourself for meaningful coverage, and finally, have an AI reviewer specifically check test quality as one more structured pass in the PR review process — with a human engineer still making the final merge decision, exactly as covered in the earlier PR-review discipline sessions. AI assists at every one of these stages. A human remains accountable for the final judgment at every one of them too."

> 🎯 **Instructor Note:** Close with a synthesis question tying the entire session together. Ask: "If you had to remove one single step from this six-step loop and still feel reasonably confident in the resulting test suite, which step would be hardest to safely remove, and why?" There is no single correct answer, but a well-reasoned response should recognize that Block 4's engineering-led review — actually checking whether tests are meaningful, not just passing — is the step doing the most direct work to prevent a false sense of security; removing the idea-generation or AI-review steps loses genuine efficiency, but removing the human review step specifically is what would actually let a suite full of hollow, always-passing tests slip through undetected.

**Recap of Block 5 before moving on:**

- AI-assisted PR review applies directly to reviewing generated tests, using the same specific-prompting discipline from earlier PR review sessions
- A prompt specifically asking whether each test checks a meaningful value and would catch a plausible real bug produces a far more useful review than a generic request
- The full practical workflow chains together idea generation, human-decided scenarios, code generation, run-and-debug validation, engineering review, and AI-assisted PR review, with a human making the final call throughout
- AI assists at every stage of this loop; human accountability for the final judgment remains at every stage as well
